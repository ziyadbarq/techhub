# Track IT services from apps to infrastructure

Service Management gives you a complete catalog of all technology services at Barq—applications, databases, APIs, cloud services, and more. Link services to business processes, track ownership, manage infrastructure details, and ensure compliance with SAMA requirements.

## Why Service Management matters

A centralized service catalog ensures:

- **Business continuity**: Know which services are critical and who owns them
- **Compliance**: Track data confidentiality and essential services for SAMA
- **Operational clarity**: Map services to infrastructure and supporting assets
- **Lifecycle control**: Plan deployments, track patches, manage decommissions
- **Accountability**: Assign technical, product, and business owners

---

## Core concepts

### Services

A **Service** represents any IT service—from customer-facing applications like Mobile Banking to infrastructure services like PostgreSQL databases. Each service includes:

- **Classification**: Type (Application, Database, API, etc.), criticality, data confidentiality
- **Ownership**: Technical, Product, and Business owners
- **Lifecycle**: Deployment date, current status, patch history, planned decommission
- **Technical details**: GitLab repository, infrastructure location, cloud provider
- **Business alignment**: Linked to business processes

**Examples**:
- Core Wallet Service (Application, Critical)
- PostgreSQL Production DB (Database, High)
- Customer Portal API (API, Critical)
- Active Directory (Infrastructure, Critical)

---

### Service Types

Services are classified by technical type:

| Type | Description | Examples |
|------|-------------|----------|
| **Application** | Software applications | Core Wallet, Mobile iOS, Business Portal |
| **Database** | Database systems | PostgreSQL, Redis, MongoDB |
| **API** | API services | Payment Gateway API, Auth API |
| **Server** | Physical/virtual servers | App Server, Web Server |
| **Network** | Network infrastructure | Firewall, Load Balancer |
| **Cloud Service** | Cloud-based services | S3 Storage, Lambda Functions |
| **Middleware** | Integration middleware | Kafka, RabbitMQ |
| **Storage** | Storage systems | NAS, SAN |
| **Endpoint** | End-user devices | VPN Client, Desktop App |
| **Other** | Other service types | Custom services |

---

### Service Status

Track where each service is in its lifecycle:

- **Production**: Live and serving users
- **UAT**: User acceptance testing
- **DR**: Disaster recovery environment
- **Development**: Development/testing
- **Planned**: Not yet deployed
- **Retired**: Decommissioned

---

### Service Ownership

Each service can have multiple owners across three types:

**Technical Owner** (Engineers, Architects)
- Responsible for technical maintenance
- Handles deployments and patches
- Primary contact for incidents

**Product Owner** (Product Managers)
- Defines features and roadmap
- Prioritizes enhancements
- Represents user needs

**Business Owner** (Business Stakeholders)
- Budget and decision authority
- Business case justification
- Strategic alignment

<Callout type="warning">
**Important**: Each ownership type should have at least one primary owner for accountability.
</Callout>

---

### Business Processes

**Business Processes** map services to business capabilities, showing how technology supports business operations.

**Examples**:
- Digital Wallet → Core Wallet Service, Mobile Apps
- Digital Payments → Payment Gateway API, Core Payments DB
- Identity Management → Active Directory, Keycloak

This mapping helps:
- Understand business impact of service outages
- Prioritize service improvements
- Plan technology roadmap aligned with business needs

### Service Infrastructure

Track where and how services run:

**Location Types**:
- **On-Premises**: Barq data centers
- **OCI Cloud**: Oracle Cloud Infrastructure
- **GCP Cloud**: Google Cloud Platform
- **AWS Cloud**: Amazon Web Services
- **Hybrid**: Mix of on-prem and cloud

**Infrastructure Details**:
- Cloud provider (OCI, GCP, AWS)
- Compartment/Project (cloud organization)
- Region (Riyadh, Frankfurt, Mumbai)
- IP address and hostname
- Backup configuration and schedule

### Classification Framework (NDMO)

Services follow the NDMO framework with three classification dimensions:

#### Data Confidentiality

| Level | Description | Examples |
|-------|-------------|----------|
| **Restricted** | PII, financial data, credentials | Core Wallet, Payment Gateway |
| **Confidential** | Internal business data | Customer Portal, CRM |
| **Internal** | Internal-only, non-sensitive | Developer Tools, Monitoring |
| **Public** | Publicly accessible | Public Website, Marketing Site |

#### Business Impact Level

| Level | Description |
|-------|-------------|
| **High** | Service outage causes immediate business disruption |
| **Medium** | Service outage causes inconvenience but not critical |
| **Low** | Service outage has minimal business impact |

#### Criticality Level

| Level | Description |
|-------|-------------|
| **Critical** | Essential for core business operations (banking/payments) |
| **High** | Important but not essential |
| **Medium** | Standard business services |
| **Low** | Nice-to-have services |

<Callout type="info">
**Essential Services**: Services marked as "Essential" MUST have Critical or High criticality. These are services like Core Banking and Payments that are vital for business operations.
</Callout>

## Common workflows

### Creating a new service

1. Navigate to **Services** in the sidebar
2. Click **Create Service**
3. Fill in basic information:
   - Name (e.g., "Customer Portal API")
   - Type (e.g., "API")
   - Description and business purpose
   - GitLab repository URL (optional)
4. Set classification:
   - Data confidentiality (Restricted, Confidential, Internal, Public)
   - Business impact level (High, Medium, Low)
   - Criticality (Critical, High, Medium, Low)
   - Mark as Essential Service if applicable
5. Set lifecycle details:
   - Current status (Production, UAT, etc.)
   - Deployment date
   - Last patch date
   - Planned decommission date (optional)
6. Link to vendor and business process (optional)
7. Click **Create**

### Adding service owners

After creating a service:

1. Open the service detail page
2. Go to the **Owners** tab
3. Click **Add Owner**
4. Select:
   - Person (from dropdown)
   - Ownership Type (Technical, Product, Business)
   - Primary Owner (check if this is the main owner for this type)
5. Click **Add**

<Callout type="tip">
**Best Practice**: Always assign at least one primary owner for each ownership type. This ensures clear accountability.
</Callout>

### Adding infrastructure details

For services with infrastructure:

1. Open the service detail page
2. Go to the **Infrastructure** tab
3. Click **Add Infrastructure**
4. Select location:
   - **On-Premises**: Specify data center location
   - **Cloud**: Select cloud provider (OCI, GCP, AWS)
5. Fill in cloud details (if applicable):
   - Compartment/Project
   - Region
6. Add network details:
   - IP address
   - Hostname
7. Configure backup:
   - Enable backup toggle
   - Set backup schedule (daily, weekly, etc.)
8. Click **Save**

### Linking services to assets

Connect services to supporting assets (servers, databases, etc.):

1. Open the service detail page
2. Go to the **Assets** tab
3. Click **Link Asset**
4. Select:
   - Asset (from dropdown)
   - Relationship type:
     - **HOSTS**: Asset hosts the service (e.g., server runs application)
     - **SUPPORTS**: Asset supports the service (e.g., database for app)
     - **DEPENDS_ON**: Service depends on asset
     - **MONITORS**: Asset monitors the service
     - **BACKS_UP**: Asset backs up the service
   - Description (optional)
5. Click **Link**

### Planning service retirement

When planning to retire a service:

1. Open the service for editing
2. Set **Planned Decommission Date**
3. Update **Compliance Notes** with retirement reason
4. Click **Save**

Services approaching decommission appear in the "Retiring Soon" list (within 90 days).

When ready to retire:

1. Open the service
2. Click **Retire Service**
3. Confirm the action
4. Status changes to **RETIRED**

<Callout type="warning">
**Note**: Essential services in Production status cannot be retired until they're no longer essential or moved out of Production.
</Callout>

## Viewing and filtering services

### Services list

The main Services page shows all services with:

- Service name and type
- Current status with color-coded badge
- Criticality level
- Primary owners
- Linked vendor
- Last patch date

**Essential services** show a special badge.

### Filtering options

Filter services by:

- **Type**: Application, Database, API, etc.
- **Status**: Production, UAT, DR, Development, Retired
- **Criticality**: Critical, High, Medium, Low
- **Vendor**: Filter by vendor
- **Owner**: Show only services you own
- **Business Process**: Filter by business process

### Search

Use the search bar to find services by name.

## Business processes

### Creating business processes

Business processes map services to business capabilities.

1. Navigate to **Business Processes**
2. Click **Create Process**
3. Fill in:
   - Code (uppercase with underscores, e.g., "DIGITAL_PAYMENTS")
   - Name (e.g., "Digital Payments")
   - Description
   - Category (e.g., "Core Banking", "Channels", "Infrastructure")
4. Click **Create**

### Linking services to processes

When creating or editing a service, select the business process from the dropdown. This creates the linkage automatically.

## Essential services and compliance

### What are Essential Services?

Essential Services are those critical for core business operations—primarily Core Banking and Payment services. These services:

- **Must** have Critical or High criticality
- **Cannot** be retired while in Production status
- Require special attention for:
  - SLA management
  - Backup and DR planning
  - Change management
  - Compliance reporting

### SAMA compliance tracking

For SAMA compliance, track:

1. **Data Confidentiality**: All services with Restricted data
2. **Business Impact**: Services with High business impact
3. **Essential Services**: Services marked as essential
4. **SLA Details**: JSON field for SLA terms and support contracts
5. **Central Register**: Include/exclude from Central Asset Register
6. **Compliance Notes**: Free-text field for compliance documentation

## Best practices

### Naming conventions

- Use descriptive names: "Core Wallet Service"
- Avoid abbreviations: Not "CWS"
- Include environment if multiple: "Customer Portal API (Prod)"
- Be consistent across similar services

### Classification guidelines

**Essential Services**:
- Only mark services as essential if they're critical for core business
- Essential services must be Critical or High criticality
- Examples: Core Banking, Payment Gateway, Authentication

**Data Confidentiality**:
- RESTRICTED: Contains PII, financial data, or credentials
- CONFIDENTIAL: Internal business data, customer information
- INTERNAL: Internal-only, non-sensitive data
- PUBLIC: Publicly accessible information

**Criticality**:
- CRITICAL: Failure causes immediate business impact (minutes matter)
- HIGH: Important but can tolerate brief outages (hours)
- MEDIUM: Standard services (can tolerate planned downtime)
- LOW: Non-critical services

### Ownership management

- Always assign at least one primary owner per ownership type
- Keep owner information current
- Review ownership quarterly
- Document ownership changes in compliance notes

### Infrastructure tracking

- Always specify location (On-Prem vs Cloud)
- For cloud services, populate compartment/project and region
- Track IP addresses for on-prem services
- Enable backup tracking for critical services
- Document infrastructure changes

### Lifecycle management

- Set deployment date when service goes live
- Track last patch date for security compliance
- Plan decommissions in advance (set planned date)
- Only use RETIRED status after full decommissioning
- Document lifecycle changes in compliance notes

### Asset relationships

Link services to supporting assets:
- Servers hosting applications (HOSTS)
- Databases supporting applications (SUPPORTS)
- External dependencies (DEPENDS_ON)
- Monitoring systems (MONITORS)
- Backup systems (BACKS_UP)

## Permissions

Access to Service Management features is controlled by permissions:

| Permission | Description | Typical Roles |
|------------|-------------|---------------|
| `SERVICES_VIEW` | View service catalog and details | All IT staff, Business users |
| `SERVICES_CREATE` | Create new services | IT Staff, IT Manager |
| `SERVICES_UPDATE` | Update service details | IT Staff, IT Manager |
| `SERVICES_DELETE` | Delete services | IT Manager, System Admin |
| `SERVICES_MANAGE` | Full service management (owners, infrastructure) | IT Manager, System Admin |
| `BUSINESS_PROCESSES_VIEW` | View business processes | All IT staff, Business users |
| `BUSINESS_PROCESSES_MANAGE` | Manage business processes | IT Manager, System Admin |

Contact your System Administrator to request permissions.
