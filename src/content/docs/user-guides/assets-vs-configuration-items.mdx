# Assets vs Configuration Items

Understanding when to track something as an **Asset**, a **Configuration Item (CI)**, or **both** is crucial for effective IT management.

<Callout type="info">
**Quick Summary:** Assets track financial value and physical inventory. CIs track technical configuration and operational relationships. Many items benefit from both perspectives.
</Callout>

---

## The Key Difference

### Assets (ITAM Focus)

**Purpose:** Financial accountability and inventory control

**Key Characteristics:**
- Has **purchase cost** and depreciation
- Tracked through **lifecycle states** (ordered, in stock, deployed, retired)
- Has **physical location** or stock assignment
- Subject to **warranty** and maintenance
- Can be **assigned to people** or departments
- Focus on **ownership and value**

**Example:** A Dell laptop purchased for $1,200 with 3-year warranty, assigned to John Smith, depreciated over 4 years.

### Configuration Items (CMDB Focus)

**Purpose:** Understanding service delivery and dependencies

**Key Characteristics:**
- Represents a **component of IT infrastructure**
- Has **technical configuration** and relationships
- Connected to **services** it supports
- Tracked for **change management** and impact analysis
- Focus on **dependencies and configuration**
- Can be **virtual** (no physical form)

**Example:** Production web server cluster with relationships to load balancer, database, and application code repository.

## Decision Guide

  <TabsList>
    <TabsTrigger value="physical">Physical Hardware</TabsTrigger>

  </TabsList>

  <TabsContent value="physical">
    ### Physical Hardware You Own

    **Recommendation:** Asset + CI (linked together)

    <Steps>
      <Step title="Create the Asset">
        Track the **physical device** as an Asset:
        - Purchase cost and depreciation
        - Serial number and warranty
        - Stock location
        - Assignment to person/department
      </Step>

      <Step title="Create the CI">
        Track the **operational role** as a CI:
        - Technical configuration (IP, specs, OS)
        - Relationships to services it supports
        - Dependencies (network, power, storage)
        - Change history
      </Step>

      <Step title="Link Them Together">
        In the CI form, link to the Asset via the **Linked Asset** field.
        This connects financial tracking with operational tracking.
      </Step>
    </Steps>

    **Examples:**
    - F5 Load Balancer appliance
    - Cisco network switch
    - Dell PowerEdge server
    - SAN storage array
    - UPS backup power unit

    <Callout type="success">
    **Best Practice:** Create both Asset and CI, then link them. This gives you complete visibility: financial (Asset) + operational (CI).
    </Callout>
  </TabsContent>

  <TabsContent value="virtual">
    ### Virtual/Cloud Resources

    **Recommendation:** CI only (+ optional Contract)

    **Why CI only:**
    - No physical hardware to depreciate
    - No purchase cost (pay-as-you-go or subscription)
    - Focus is on configuration and relationships
    - Cost tracked via Contracts or License Management

    **Examples:**
    - AWS Application Load Balancer (ALB/ELB)
    - Azure Virtual Machine
    - Google Cloud Storage Bucket
    - Kubernetes cluster
    - Cloud database instance (RDS, Azure SQL)
    - Virtual network (VPC, VNet)

    <Callout type="warning">
    **Common Mistake:** Don't create Assets for cloud resources unless you purchase reserved instances with upfront payment that needs depreciation tracking.
    </Callout>

    **Track costs via:**
    - **Contract:** Monthly/annual cloud subscription
    - **License:** For software licenses (Office 365, Adobe Creative Cloud)
  </TabsContent>

  <TabsContent value="software">
    ### Software on Existing Hardware

    **Recommendation:** CI only (linked to server Asset)

    **Why:**
    - The **server is already the Asset**
    - The **software is a CI** representing its operational role
    - Use License Management for software costs

    **Examples:**
    - NGINX load balancer on your server
    - HAProxy on your server
    - Apache Tomcat application server
    - PostgreSQL database
    - Monitoring agent (Prometheus, Datadog)

    <Steps>
      <Step title="Ensure Server Asset Exists">
        The physical server should already be tracked as an Asset.
      </Step>

      <Step title="Create CI for Software">
        Create a CI representing the software instance:
        - CI Class: "Application" or "Database"
        - Link to server Asset: "Runs on"
        - Configuration: version, settings, ports
      </Step>

      <Step title="Track License Separately">
        If the software requires a license, use **License Management** to track:
        - License entitlements
        - Cost and renewal
        - Compliance
      </Step>
    </Steps>
  </TabsContent>
</Tabs>

## Common Questions

### "Why create both Asset and CI for the same thing?"

**Different perspectives, different needs:**

**Finance/Procurement needs (Asset):**
- "How much did we spend on network equipment?"
- "When does the warranty expire?"
- "What's the current depreciated value?"
- "Who is responsible for this device?"

**IT Operations needs (CI):**
- "What services will be impacted if this fails?"
- "What other systems depend on this?"
- "What's the current configuration?"
- "What changes were made last week?"

By creating both and linking them, you satisfy both needs while maintaining a single source of truth.

### "Can a CI exist without an Asset?"

✅ **Yes!** Many CIs have no physical form or purchase cost:

- Cloud resources (AWS, Azure, GCP)
- Virtual machines
- Software instances
- Network configurations
- API endpoints
- SaaS applications
- Business services

### "Can an Asset exist without a CI?"

✅ **Yes!** Some assets don't need operational tracking:

- Office furniture (desk, chair)
- Non-IT equipment (printer for office use)
- Spare parts in stock
- Assets not yet deployed
- Decommissioned equipment

### "How do I link an Asset to a CI?"

<Steps>
  <Step title="Navigate to CI">
    Go to **Configuration Items** → select or create your CI
  </Step>

  <Step title="Find Linked Asset Field">
    In the CI form, find the **Linked Asset** field
  </Step>

  <Step title="Search and Select">
    Search for your Asset by tag or serial number, then select it
  </Step>

  <Step title="Save">
    Save the CI. The link is now established.
  </Step>
</Steps>

The CI will now show the linked Asset, and the Asset detail page will show the related CI.

## Best Practices

<Callout type="success">
**Do:**
- Create both Asset + CI for physical hardware you own
- Always link CIs to their underlying Assets when applicable
- Use CIs to model virtual/cloud resources
- Use Contracts to track cloud subscriptions
- Use License Management for software costs
</Callout>

<Callout type="warning">
**Don't:**
- Create Assets for cloud resources (unless reserved instances with upfront cost)
- Duplicate cost tracking in both Asset and License/Contract
- Create CIs for office furniture or non-IT equipment
- Forget to link CIs to Assets when both exist
</Callout>

---

## Summary

**The Rule of Thumb:**

```
Physical hardware you own = Asset + CI (linked)
Virtual/Cloud resource = CI only (+ Contract for costs)
Software on your server = CI only (linked to server Asset)
Office equipment = Asset only
```

**When in doubt:**
1. Does it have a **purchase cost** and need **depreciation**? → Asset
2. Does it have **technical configuration** and **service relationships**? → CI
3. Both? → Create both and link them together
